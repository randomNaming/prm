# 上服务器 + 手机端访问：需求评审

> 状态：**评审稿，未实现任何代码**。
> 目的：在动手之前把需求、风险与顺序理清。看完请回答第五节那五个问题。

---

## 一、结论摘要

1. **「前后端传输加解密」这个提法把三件不同的事混在了一起。** 如果担心的是「客户资料在公网上传被人截获」，那答案是 **HTTPS**，不是应用层加解密 —— TLS 已经把这件做了，再套一层只是重复劳动。
2. **真正的前置阻塞不是加密，是「没有认证」。** 这个系统从设计上就没有「谁」的概念，22 个接口全部裸奔。加密解决不了这件事：服务端必须解密才能干活，没有认证的话，任何拿到地址的人都能读走全部客户资料。
3. **要做微信小程序，有两道硬门槛**：强制 HTTPS + **域名备案**（国内主体）。这跟加解密无关，是资质与合规问题，得先确认你满不满足。
4. **移动端建议先做响应式 Web（PWA），不要一上来做小程序。** 现在整套界面是 Element Plus + 表格，小程序里用不了，等于重写一遍 UI。而响应式 Web 改样式就行，能先把你真正缺的「手机上能看能改」跑通。

## 三、关键判断：「加解密」被当成了三件事

「做好前后端传输过程中加解密」这句话，对应的其实是三个不同的威胁模型和三种不同的做法。**先选威胁模型，再选技术，否则会做出又贵又没用的东西。**

| 你想防的是 | 正确做法 | 应用层加解密有用吗 |
| --- | --- | --- |
| **① 路上被人偷看**（公共 WiFi、运营商、中间人） | **HTTPS / TLS** | ❌ 没用。TLS 已经做了，再套一层只是重复 |
| **② 服务器被拖库**（磁盘被拿走、运维偷看） | **静态加密**：磁盘加密 + 敏感列加密 + 密钥与数据分离 | ❌ 没用。这是存储层的事，跟传输无关 |
| **③ 连服务端都不该看到明文**（端到端） | 客户端持密钥，服务端只存密文 | ✅ 有用，**但代价极大**：服务端没法搜索、排序、做关联查询、没法让智能体抽取字段 —— 等于放弃这个产品的核心能力 |
| **④ 有人冒名访问** | **认证 + 授权** | ❌ 完全没用 |
| **⑤ 请求被篡改 / 重放** | TLS + 时间戳 + nonce + 签名 | ⚠️ 只有「没有 TLS」或「端到端防篡改」时才需要 |

**我的判断：你担心的是 ①。那答案就是 HTTPS，不需要写任何加解密代码。**

真正需要写加解密的只有两种情况：

- **端到端（③）**：只有在「你连自己的服务器都不信任」时才成立。但你的服务器要跑智能体去读聊天记录、抽字段、做后台研究 —— 服务端看不到明文，这一整套就没了。**不建议。**
- **个别字段（②的变体）**：比如
  - `messages.content`（聊天原文）：**不参与搜索、不参与排序，只是留底** → **可以加密**，代价很小，收益实在。这是最值得做的一处。
  - `contacts` 的姓名/电话/邮箱：**要参与搜索**（`listContacts` 按姓名/邮箱/微信号做子串匹配）→ 加密后搜不了，要用盲索引，复杂度高、收益有限。**不建议。**

## 四、真正要评审的清单

### P0 · 认证 —— 不做就绝对不能上手机

这是唯一的硬阻塞。最简可行方案（单人系统，不需要多用户那套）：

- 一个长期有效的访问凭证（API Key 或 token），放在请求头里。
- **一设备一 token，可单独吊销** —— 手机丢了能立刻掐掉那一台，而不是换掉全部。
- 「记住登录」需要能续期：短期 access token + 长期 refresh token，或长有效期 token + 服务端可撤销列表。
- 落点：`server/middleware/auth.ts`（现在这个目录不存在，要新建）。放中间件而不是逐个接口加，22 个接口才不会漏。
- **注意例外**：`POST /api/intake` 是给 `mcp-crm` 调的（本机 stdio），加认证后 `mcp-crm/.env` 里的 `CRM_BASE_URL` 那一侧也要带上凭证。

### P0 · HTTPS

- 需要**域名 + 证书**。如果要做小程序，这是**强制**的，且自签证书小程序不认。
- 反代要保留 `proxy_buffering off`，否则流式回答会攒到最后一次性吐出（README 已注明）。
- 顺带补上安全响应头（`X-Content-Type-Options`、`X-Frame-Options` 等），现在一个都没有。

### P1 · 敏感字段治理

- `.env` 里的 MySQL 密码与 ZAI 密钥：上服务器后要考虑放哪（至少文件权限收紧，进一步可用系统 keyring / 环境注入）。
- `messages.content` 列级加密：值得做（见第三节），但要先确认「留底只读、不参与搜索」这个前提不變。
- 日志脱敏：现在没有集中日志，先定规矩即可。

### P1 · 编辑冲突

手机和电脑可能同时改同一条联系人。现在**没有任何版本号或乐观锁**，后写的直接覆盖先写的。单人使用冲突概率低，但「手机上改了一半、电脑上又保存」会静默丢改动。建议加一个 `updatedAt` 比对（已经有 `updatedAt` 字段，用得上）。

### P2 · 移动端形态

| 形态 | 成本 | 限制 |
| --- | --- | --- |
| **响应式 Web / PWA** | **最低**。现有 6 个页面改样式 | 无需备案、无需审核；推送与离线能力弱 |
| **微信小程序** | **高**。要重写全部界面（Element Plus 用不了） | 免安装、微信内好转发；**强制 HTTPS + 域名备案 + 审核** |
| **原生 App** | 高 | 可推送、可离线；要上架 |

**两个被低估的具体技术风险（做小程序才会遇到）**：

1. **界面要重写**。现在是 Element Plus + `el-table`，小程序没有 DOM，整套组件用不了。
2. **流式输出**。智能体对话走 SSE（`EventSource`），**小程序不支持 `EventSource`**，得改用 `wx.request` 的 `enableChunked` 或 WebSocket。这不是改个配置的事，要重做一条链路。

**建议**：第一步做**响应式 Web**，把认证与 HTTPS 做扎实，先满足「手机上能看能改」。小程序作为第二阶段，等你确认了域名备案再说。

### P3 · 运维

- 备份：`scripts/backup.sh` 已有，但没上定时任务。
- 限流：现在没有，公网暴露后建议在反代层加。
- 进程守护：README 给了 systemd 与 pm2 示例，可直接用。

## 五、需要你拍板的五个问题

1. **威胁模型是第几类？**（① 路上被偷看 / ② 服务器被拖库 / ③ 连服务端都不能看到明文）
   → 我猜是 ①，那就不需要写加解密代码，只需要 HTTPS。如果是 ③，产品能力要打折，得单独谈。

2. **手机端先做哪个形态？** 响应式 Web / 小程序 / App。
   → 我建议响应式 Web。

3. **有没有已备案的域名？**（决定小程序现在能不能做）

4. **服务器放哪？** 自己的 NAS / 国内云 / 境外云。
   → NAS 暴露公网风险最高（家里网络、无专业运维），建议只走内网或 VPN；公网放云服务器。

5. **能接受「服务端能看到明文」吗？**
   → 绝大多数 CRM 都接受。如果不接受，智能体那套要做大改。

## 六、建议的推进顺序

```
P0  认证（一设备一 token，可吊销）      ← 不做这个，其余都是白做
P0  HTTPS + 域名                        ← 小程序的前置门槛
P1  响应式移动端适配                     ← 先让手机能用
P1  messages 列级加密 + 密钥治理
P2  编辑冲突（乐观锁）
P2  小程序（视备案情况，需重写 UI 与流式链路）
P3  备份定时、限流、日志脱敏
```

**一句话总结**：先解决「谁能进」，再解决「路上安全」（HTTPS），最后才轮到「服务器上怎么存」。应用层加解密这件事，除非你要做端到端（③），否则不需要 —— 把力气花在认证和 HTTPS 上，收益大得多。
